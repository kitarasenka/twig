## Что сверено на живом git (2.54.0), а не по памяти

- `\ No newline at end of file` идёт **строкой ниже** той строки, к которой
  относится, и относится именно к ней.
- Пропущенный счётчик в заголовке означает 1: `@@ -1 +1 @@`. Удаление файла —
  `@@ -1 +0,0 @@`, добавление — `@@ -0,0 +1 @@`.
- Бинарный файл: `Binary files a/x and b/x differ`, hunk'ов нет.
- **При пробеле в имени git ставит TAB после пути** в строках `---`/`+++`,
  а строка `diff --git a/sp ace.txt b/sp ace.txt` остаётся принципиально
  неоднозначной. Поэтому пути из патча не парсятся вообще: вызывающий код и
  так знает путь, потому что сам передал `-- :(literal)<path>`. Это убирает
  целый класс ошибок с путями, а не смягчает его.
- `git apply --cached` принимает завершающий TAB и для путей без пробелов —
  проверил отдельно обе ветки, поэтому конструктор ставит TAB всегда.

## Найденная ошибка, которую тест бы пропустил

Первая версия конструктора пересчитывала номера строк только для staging.
На самом деле при `--reverse` git сопоставляет с индексом **новую** сторону
патча, а не старую, поэтому зеркалить надо не только классификацию строк, но
и арифметику: сторона, по которой идёт сопоставление, сохраняет разобранные
номера, а синтетическая сторона смещается на накопленную дельту.

Отдельно важно, что **этот баг не ронял `git apply`**: он ищет контекст вокруг
указанной строки и молча применял патч со сдвигом. То есть сквозной тест
«применилось и в индексе то, что нужно» его не ловил. Поэтому в проверке есть
прямой ассерт на текст заголовка `@@` для случая, где `oldStart ≠ newStart`.

## Семантика частичного выбора

Ядро вехи, зеркальное по направлениям (как в `git add -p`):

| Строка | staging (`reverse: false`) | unstaging (`reverse: true`) |
|---|---|---|
| выбранная | остаётся как есть | остаётся как есть |
| невыбранная `add` | выбрасывается | становится контекстом |
| невыбранная `delete` | становится контекстом | выбрасывается |
| контекст | контекст | контекст |

Обоснование: при staging старая сторона патча — это индекс, и невыбранное
удаление обязано в индексе остаться; при unstaging новая сторона — это индекс,
и невыбранное добавление в нём уже есть и обязано пережить обратное применение.

macOS arm64 / Node 20.20.0 / git 2.54.0.

`diff-parser.mjs` покрывает: пустой диф, обычное изменение, отсутствующий
перевод строки в конце, пропущенные счётчики, добавление и удаление файла,
бинарный файл, несколько hunk'ов, заголовок функции после `@@`, пустую
контекстную строку, CRLF, кириллицу и emoji; ошибки — не-строка, счётчик не
сходится с числом строк, неизвестный префикс, два файла в одном патче,
маркер no-newline без строки, бинарный патч с hunk'ами; отдельный ассерт, что
сообщение об ошибке не содержит содержимого файла (проверено на строке,
похожей на утёкший секрет). Плюс argv-билдеры, включая пути, похожие на флаг
(`--upload-pack=evil`) и на glob (`weird[*].txt`), и отказ на `..`, ведущем
`/`, NUL и не-строке.

`patch-builder.mjs` — сначала чистая логика (пустой выбор → `null`, выбор
только контекста → `null`, битые селекторы → ошибка, TAB в заголовке,
зеркальность классификации и нумерации), затем настоящий временный
репозиторий: staging одного hunk'а из двух, staging одной добавленной строки
из hunk'а, где есть ещё и правка, staging обоих hunk'ов сразу (проверка
дельты), unstaging двух строк через `--reverse`, файл без финального перевода
строки, добавленный файл с пробелом в имени через `git add -N`, и разбиение
рабочего дерева на staged/unstaged/untracked, когда один файл попадает и в
staged, и в unstaged. После каждого шага сверяется точное содержимое индекса
(`git show :<path>`), а не только код возврата.

## Отступление от правила «в самопроверках Git не запускать»

В M1 и M2 самопроверки Git не запускали. Здесь `patch-builder.mjs` запускает:
единственное настоящее доказательство корректности патча — что его принимает
`git apply --cached` и в индексе оказывается ровно выбранное. Прецедент в
модуле есть (`git-exec.mjs`, `commit.mjs` — оба создают временный
репозиторий). Все мутации происходят внутри временного каталога, который
удаляется в `finally`; код модуля по-прежнему ничего не мутирует.

## Расхождения с контрактом, который я же написал

1. **`FilePatch` получил поле `mode`** (`new file mode`/`deleted file mode`).
   В контракте его не было — понадобилось, когда выяснилось, что патч для
   добавленного файла без строки режима `git apply` принимает не всегда.
   Не стал подгонять реальность под текст, написанный часом раньше.
2. **`buildPatch` принимает `added`/`deleted`/`mode`** сверх контракта — по
   той же причине. Частично застейдженное удаление перестаёт быть удалением,
   поэтому `+++ /dev/null` ставится, только если выбраны все hunk'и и новая
   сторона пуста.
3. **В `buildDiffArgv` добавлен `--no-renames`.** При обнаруженном
   переименовании один патч описывает два разных пути, а конструктор собирает
   заголовок из одного — инвариант «один патч = один путь» сломался бы.
   Переименования UI всё равно видит: `parseStatusV2` отдаёт `originalPath`.

## Аудит безопасности

- Мутаций нет: модуль только читает (`status`, `diff`). Всё через
  существующий `runGit` (`spawn`, `shell: false`), новых точек запуска нет.
- `buildDiffArgv` валидирует путь (не пустой, ≤32768, без NUL, без ведущего
  `/`, без сегмента `..`) и передаёт его как `:(literal)<path>` после `--`,
  так что путь, похожий на флаг или на glob, остаётся путём. Покрыто тестами.
- Сообщения об ошибках парсера и конструктора — статические литералы: в дифф
  попадает содержимое исходников пользователя, и оно не должно утекать в
  текст ошибки, лог или консоль команд. Проверено ассертом.
- Патч в проверке пишется во временный каталог **вне** рабочего дерева и
  удаляется в `finally`.

## Аудит производительности

- Парсер — один линейный проход по строкам, без вложенных сканирований и без
  регулярок по всему входу (regex применяется только к строке заголовка).
- Конструктор — один проход по выбранным hunk'ам; сортировка выбора
  `O(k log k)` по числу выбранных hunk'ов, не по размеру файла.
- `loadWorktree` — один вызов `git status` на всё дерево, не по файлу на
  запрос; `loadWorktreeDiff` — один вызов на открытый файл. N+1 нет.
- Диффы на десятки тысяч строк живьём не гонял: самый крупный случай в
  проверке — 20-строчный файл. Виртуализацию длинного диффа делает Codex,
  ориентир — `content-visibility: auto`, как в M2.

## Ограничения и открытые вопросы

- **Новые проверки не подключены в `npm test`** — по разбивке это шаг Codex,
  и делать его сейчас смысла нет: Codex добавит собственные проверки M3 и всё
  равно будет править ту же строку. Если Codex к M3 не приступит, подключить
  надо будет отдельно, иначе повторится ситуация M2, когда проверки лежали
  рядом с `npm test`, но не в нём.
- **У `runGit` нет stdin**, поэтому `git apply --cached` придётся кормить либо
  временным файлом вне репозитория (как в моей проверке), либо расширенным
  `runGit` с необязательным `stdin`. Рекомендую второе: патч не попадает на
  диск. Файл `exec.js` — за Codex.
- **Unstaging на unborn-ветке**: `git restore --staged` падает без HEAD, нужен
  `git rm --cached`. Признак есть — `parseStatusV2` отдаёт `branch.unborn`.
- **Untracked-файл по hunk'ам** стейджится только после `git add -N` (мутация,
  сторона Codex); целиком — обычный `git add`.
- **Краевой случай без финального перевода строки**: если в одном hunk'е
  выбрать удаление строки, но не выбрать парное добавление с маркером
  no-newline, получившийся конец файла неоднозначен. `git add -p` ведёт себя
  там так же неуверенно. Патч в этом случае либо применится корректно, либо
  будет отвергнут `git apply` — тихой порчи файла не будет, но UI стоит не
  предлагать такой выбор как обычный.
- Windows/Linux не запускались. `core.autocrlf` в патчах не подменяю: патч
  строится из вывода того же `git diff`, содержимое согласовано.

## Передать Codex

Готов read-only Git-слой рабочего дерева: `loadWorktree` (staged/unstaged/
untracked + `branch`), `loadWorktreeDiff` (разобранный патч файла),
`parseFilePatchV1` и `buildPatch` для staging и unstaging по строкам и
hunk'ам. Твоя половина M3 и четыре предупреждения, которые сэкономят время
(нет stdin у `runGit`, unborn-ветка, `git add -N` для untracked,
`core.autocrlf`), расписаны в `tasks/M3-STAGING.md` — там же выводы
дизайн-скилла по экрану изменений. M3 целиком не завершён: мутаций, IPC, UI,
commit/stash/pull/push и интеграции ещё нет.

## Как закрыты четыре предупреждения из задания

1. **stdin у `runGit`** — добавлен необязательный `stdin`, выбран он, а не
   временный файл: патч и сообщение коммита не попадают на диск. В журнал
   пишется только размер (`… · N bytes on stdin`), потому что содержимое —
   это исходники пользователя, а журнал персистится. Пометку положил в
   подпись операции, а не в поток вывода: консоль не должна выдавать её за
   вывод git.
2. **Unborn-ветка** — `buildUnstageArgv(path, unborn)` даёт
   `git rm --cached` вместо `restore --staged`. В проверке отдельно
   зафиксировано, что `restore --staged` в этом состоянии действительно
   падает, — иначе тест ничего не доказывал бы.
3. **Untracked по hunk'ам** — открытие untracked-файла в UI сначала делает
   `git add -N`, после чего строки становятся выбираемыми.
4. **`core.autocrlf`** — переводы строк нигде не нормализуются; патч
   строится из вывода того же `git diff`.

## Решение по безопасности, которого не было в задании

Renderer **не присылает содержимое патча**. Канал `worktree:apply` принимает
путь, флаг стороны, `digest` диффа и индексы строк; main перечитывает дифф
сам, сверяет отпечаток и только потом собирает патч. Два следствия:

- в индекс не может попасть содержимое, которого Git только что сам не выдал;
- выбор, сделанный на устаревшем диффе, отвергается с внятной ошибкой вместо
  того, чтобы застейджить не те строки.

Для этого `loadWorktreeDiff` теперь возвращает `digest` (sha256 сырого
вывода). Это расширение контракта из `M3-STAGING.md`, зафиксировано здесь.

## Что нашли тесты (а не ревью)

- **Сквозной прогон поймал реальный баг навигации**: `onChanged` вызывал
  `reload` истории, а тот сбрасывал `selected`, и экран рабочего дерева
  размонтировался сразу после staging'а. Починено сохранением выбора
  `worktree` при перезагрузке.
- **Плохое доступное имя кнопок**: `Button` собирает `aria-label` только из
  строковых детей, поэтому число выпадало и получалось «Commit   file».
  Исправлено в компонентах (одна строка-шаблон), а не обходом в тесте.
- **`min-height` на списках сделал кнопку Commit недостижимой** при
  раскрытой консоли — форма уходила за пределы обрезанного контейнера.
  Откатил: достижимость важнее плотности, в CSS оставлен комментарий почему.
