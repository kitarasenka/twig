# M1-STATUS: результат

Задача выполнена в границах, указанных в `tasks/M1-STATUS.md`. Файлы вне списка
не трогал; параллельные правки Codex (`main/git/exec.js`, `main/git/repository.js`,
`main/git/askpass.cjs`, `main/command-log.js`, `main/store.js`,
`scripts/checks/git-exec.mjs`) не читал и не менял.

## Файлы

- `main/git/status-parser.js` — единственный экспорт `parseStatusV2(output)`,
  плюс экспорт класса `StatusParseError` (нужен вызывающему коду, чтобы отличать

- `scripts/checks/status-parser.mjs` — самостоятельный чек на `node:assert/strict`,
  без Jest, без запуска Git. Все фикстуры — литералы прямо в скрипте, отдельная
  папка `fixtures/status/` не понадобилась.
- `tasks/M1-STATUS-RESULT.md` — этот файл.

## Источник истины

Формат сверен с `git help status` (раздел «Porcelain Format Version 2») на
установленной версии `git 2.54.0`, включая реальный `git status --porcelain=v2
--branch -z` в этом checkout — сверил байты через `od -c`. Ключевой момент:
при `-z` у record type 2 сначала идёт `<path>` (целевой путь), затем NUL, затем
`<origPath>` — порядок обратный интуиции «откуда куда», код и тесты явно это
проверяют отдельным кейсом.

## Контракт

Реализован как в задаче, без отклонений от заявленной формы результата:

```js
export function parseStatusV2(output) {
  return {
    branch: { oid, name, detached, unborn, upstream, ahead, behind },
    entries: [{ kind, path, originalPath, indexStatus, worktreeStatus, submodule, score }]
  };
}
```

Разбор построен на одном линейном проходе: `output.split('\0')`, затем обход
токенов; record type 2 при обработке дополнительно поглощает следующий токен как
`originalPath`. Заголовки, записи 1/2/u/?/! — как в спеке. Поля mode/hash (mH,
mI, mW, hH, hI и стадии u-записей) синтаксически валидируются (восьмеричный
режим, hex 40/64 байта), но не попадают в результат — контракт их не запрашивает.

## Расхождения с контрактом (не менял его молча, решения принял сам)

1. **Экспортирован `StatusParseError`.** Контракт называет только
   `parseStatusV2`. Без именованного класса ошибки вызывающий код не сможет
   надёжно отличить «Git прислал неожиданный формат» от программной ошибки —
   а разделять их придётся: одно значит «баг парсера/новая версия Git», другое
   «баг в другом месте». Если Codex/пользователь хотят строго один экспорт —
   легко заменить на `error.name === 'StatusParseError'` без изменения формы.
2. **Тип ошибки для нестрокового `output`.** Есть соблазн бросить `TypeError`
   по конвенции JS, но выбрал тот же `StatusParseError` — вызывающему коду
   удобнее ловить один тип ошибок из этого модуля. При необходимости меняется
   в одну строку (`fail` → `throw new TypeError(...)`), тест придётся
   поправить на `TypeError` в этом одном ассерте.
3. **Заголовок `# stash N` явно не поддержан**, хотя он «известный» в
   документации Git — в контракте о нём ничего не сказано, и он не относится
   к `branch`. Обрабатывается как любой нераспознанный заголовок: пропускается
   молча (this is «forward-compat», не «invalid-header»). Если понадобится
   `branch.stashCount` — расширяется на 3-4 строки в `parseHeader`.
4. **XY-алфавит валидируется по набору символов, не по конкретным разрешённым
   парам.** Например, `MM` разрешён и для ordinary, и технически git его не
   печатает в этой комбинации на практике, но спека не документирует closed-set
   пар — только допустимые символы (`. M T A D R C U` для обычных/rename,
   `D U A` для unmerged). Более строгая проверка «только реальные git-комбинации»
   рискует отвергать корректный вывод будущих версий git; выбрал более мягкий,
   но проверяемый инвариант.

Если что-то из этого нужно ужесточить или наоборот — контракт не менял, жду
решения при интеграции.

## Проверки

```
$ node scripts/checks/status-parser.mjs
status-parser: all checks passed

$ ./node_modules/.bin/eslint main/git/status-parser.js scripts/checks/status-parser.mjs
(без вывода — чисто)
```

Оба выполнены из `modules/git_desk/` на macOS arm64 / Node 20.20.0 / git 2.54.0.

Покрытие самопроверки:
- пустой вывод; полный набор branch-заголовков; detached HEAD; unborn branch
  (`(initial)`); отсутствие upstream; SHA-1 и SHA-256 `branch.oid`;
  неизвестные заголовки (`# branch.mystery-field`, `# stash 3`) — пропускаются,
  не роняют парсер;
- rename (score `R100`) и copy (score `C75`) с проверкой порядка path/origPath
  при `-z`;
- пути с пробелами, табами, переводом строки, обратным слэшем, кириллицей,
  emoji и ведущим дефисом — байт в байт, без trim/split;
- имя файла, текстуально совпадающее с заголовком/записью (`# branch.oid
  deadbeef` как реальное имя untracked-файла; поддельная rename-запись как
  `originalPath`) — подтверждает, что диспетчеризация идёт по позиции токена,
  а не по содержимому;
- все 7 XY-комбинаций конфликтов unmerged (`DD AU UD UA DU AA UU`);
- ignored-запись;
- грязный submodule (`SCMU`, `S..U`) — не схлопывается в обычный файл;
- ошибки: не-строка на входе, оборванная запись (нет конечного NUL), неизвестный
  тип записи, битые `branch.ab`/`branch.oid`/`branch.head`, пустая запись между
  NUL, rename-запись без второго токена (`originalPath`), запись с недостатком
  полей, битое поле submodule, rename-score вне 0..100 и с недопустимой буквой,
  unmerged с недопустимым XY;
- сообщение об ошибке не содержит исходных данных (путей, хэшей) — отдельный
  ассерт на конкретном кейсе с «секретным» путём в имени файла.

## Аудит безопасности

- Ноль запусков процессов, ноль обращений к `fs`/сети/Electron API — чистая
  функция над строкой. Спека требовала именно этого.
- Сообщения об ошибках — статические литералы, нигде не интерполируют входные
  данные (пути, хэши, содержимое строки). Проверено тестом.
- Парсинг не использует `RegExp` с пользовательским вводом внутри паттерна
  (только вход целиком матчится к фиксированным regex) — исключён ReDoS через
  катастрофический backtracking на длинных путях.
- Опасные имена файлов (полные поддельные заголовки/записи в качестве пути)
  не приводят к путанице границ токенов — разбор от начала до конца управляется
  позицией в массиве токенов, а не повторным сканированием содержимого.

## Аудит производительности

- Один линейный проход: `String.prototype.split('\0')` — O(n), затем один
  `for`-цикл по токенам без вложенных сканирований всего входа. `splitFields`
  находит фиксированное малое число (≤10) пробелов на запись через `indexOf` —
  не квадратичный по числу файлов.
- Никаких промежуточных копий всего вывода (только `slice` на уровне отдельных
  токенов/полей). Для многотысячных `git status` на больших репозиториях это
  должно линейно масштабироваться, но реальных больших выводов не гонял —
  только синтетические фикстуры из самопроверки.

## Ограничения

- Не проверял поведение на реальном выводе `git status` вне этого checkout
  (Windows/Linux, экзотические конфигурации git — `core.quotePath`, стадии
  submodule с частичным клонированием и т.п.) — задача явно запрещает запуск
  Git из этой части M1.
- Валидация mode/hash-полей синтаксическая (формат), не семантическая
  (например, не проверяю, что режим `160000` (gitlink) действительно
  сопровождается submodule-полем `S...`, а не `N...`) — контракту это не нужно,
  но если Codex в `exec.js`/`repository.js` рассчитывает на такую перекрёстную
  проверку, её тут нет.
- `score.value` не проверяет отсутствие ведущих нулей (`R007` формально прошёл
  бы как значение 7) — git такого не печатает, но парсер это не отвергнет.
  Не стал добавлять это ограничение, так как оно не в списке требований и не
  создаёт риска для потребителя.

## Передать Codex

`main/git/status-parser.js` готов: `export function parseStatusV2(output)` и
`export class StatusParseError`. Вход — сырая UTF-8 строка из
`git status --porcelain=v2 --branch -z` (буфер из `exec.js` привести к строке
до вызова, парсер сам ничего не декодирует и Git не запускает). Формат
результата — как в `tasks/M1-STATUS.md`, без отклонений, три пункта решений
описаны выше в «Расхождения с контрактом» (действующий экспорт
`StatusParseError` — единственное, что физически не совпадает 1:1ное с
контрактом, и это осознанный выбор, не молчаливое расширение API). Самопроверка
не запускает Git и не трогает `exec.js`/IPC — интеграцию в общий `npm test` и
документацию делает Codex. M1 в целом не завершён — это только кусок парсера.
